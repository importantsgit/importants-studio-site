공개 저장소에 남겨 둔 운영 규칙

2026년 9월 21일Importants Studio

2026-09-21

블로그는 GitHub Pages로 돌립니다. 무료로 쓰려면 저장소가 공개여야 해서, 저장소 8개를 전부 공개로 두고 있었습니다. 조직 이름은 private으로 시작하는데, 그 안의 저장소는 공개인 상태였습니다.

사이트를 공개하는 일과 작업 규칙을 공개하는 일을 따로 생각하지 않았습니다. GitHub Pages가 저장소를 요구하니 그 안에 필요한 파일을 넣는 방식으로 계속 작업했습니다. 저장소에 들어 있는 파일을 다시 살펴보다가, 글과 함께 공개할 이유가 없는 문서까지 같이 들어가 있다는 점을 확인했습니다.

공개 상태였던 파일

첫 번째는 글 쓰는 규칙을 적은 문서였습니다. 4,600자 분량의 AI 티 금지 목록입니다. 문장 끝, 소제목, 서론과 결론의 형태처럼 글에 남는 흔적을 피하려고 적어 둔 규칙이었습니다.

두 번째는 에이전트 운영 규칙 파일이었습니다. 2,800자짜리였고, 프런트매터 형식, 출처 2개 이상 규칙, 커밋 규칙, 테마에서 빠지기 쉬운 함정까지 들어 있었습니다. 에이전트가 어떤 순서로 작업하고 어디에서 멈춰야 하는지 적어 둔 파일이었습니다.

아직 만들지 않은 도구 후보를 적어 둔 목록도 있었습니다. 공개 저장소에서 글을 발행하려고 만든 구조 안에, 글과 직접 관계없는 작업 목록과 운영 규칙이 함께 있었습니다.

글쓰기 규칙은 읽는 사람이 내용을 해석해야 합니다. 반면 에이전트 운영 규칙 파일은 그대로 복사한 뒤 경로만 맞추면 작업에 붙일 수 있습니다. 공개해도 되는 사이트 파일과 공개할 필요가 없는 설정 파일을 같은 기준으로 처리한 판단은 틀렸습니다.

파일을 옮긴 뒤에도 남은 것

옮기는 작업 자체는 간단했습니다. 비공개 파이프라인 저장소에 폴더 하나를 만들고 파일을 넣었습니다. 그다음 프롬프트가 공개 저장소 안의 파일이 아니라 그 폴더의 절대 경로를 읽도록 바꿨습니다.

먼저 헤드리스 에이전트가 작업 폴더 밖의 경로를 읽을 수 있는지 실험했습니다. 읽혔습니다. 이 확인이 없었다면 파일을 옮겨도 기존 자동 읽기 방식을 그대로 써야 했을 수 있습니다.

자동으로 읽히던 파일 셋은 프롬프트에 해당 파일을 먼저 읽으라는 단계를 넣어 대체했습니다. 나머지 블로그 셋은 원래 그 파일 없이도 돌아가고 있었습니다. 같은 방식이 이미 검증된 셈이었습니다.

다만 공개 저장소에서 파일을 지웠다고 과거 커밋까지 사라진 것은 아닙니다. 커밋 주소를 알면 지금도 파일을 받을 수 있습니다. 저장소 기록을 다시 쓰면 지울 수 있지만, 되돌릴 수 없는 작업이라 하지 않았습니다. 이 부분은 그대로 남아 있습니다.

베끼는 걸 걱정하면서 정작 제일 베끼기 좋은 형태로 올려두고 있었습니다. 글로 쓴 설명은 읽고 해석해야 하지만 설정 파일은 복사해서 바로 돌립니다.
