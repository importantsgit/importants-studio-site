## 처음에는 구조가 단순해 보였습니다

main에 직접 push하지 않고 머지가 곧 발행이 되게 잡은 구조에서, 매일 10시 30분에 launchd가 셸 스크립트를 실행하면 스크립트가 claude CLI를 헤드리스로 띄워 글을 쓴 뒤 GitHub PR을 열도록 했고, 이 부분은 처음부터 바꾸지 않았습니다.

터미널에서는 흐름이 이어졌습니다. 그래서 launchd에 등록하면 끝날 줄 알았습니다.

첫 번째로 멈춘 곳은 스크립트 위치였습니다. 스크립트를 바탕화면 폴더에 뒀는데 launchd가 읽지 못했습니다. 바탕화면은 눈에 잘 들어오고 파일을 꺼내기 편해서 골랐습니다. 자동 실행하는 스크립트도 거기에 두면 관리하기 쉽다고 생각했습니다.

바탕화면을 보호 영역으로 잡는 macOS의 TCC 때문에 launchd가 그 위치의 스크립트를 읽지 못해, 스크립트를 `~/blog-automation`으로 옮긴 뒤 바탕화면에는 심볼릭 링크만 뒀습니다.

이제 위치는 정리됐습니다. 다음에는 명령이 사라졌습니다.

## 터미널의 환경은 따라오지 않았습니다

터미널에서 되던 `claude` 명령이 launchd 환경에서는 없는 명령이었습니다. launchd는 로그인 셸의 PATH를 물려받지 않습니다. 터미널에서 명령이 된다는 사실만 확인한 채 자동 실행 쪽에도 같은 PATH가 있다고 생각한 판단이 틀렸습니다.

스크립트 안에서 PATH를 직접 지정했습니다. 터미널 래퍼에 기대지 않고 실제 바이너리 경로인 `~/.local/bin/claude`를 쓰게 했습니다. launchd가 실행하는 셸과 터미널에서 쓰는 셸을 같은 것으로 취급하면 안 됐습니다.

`claude`가 실행된 뒤에는 Git에서 다시 멈췄습니다. 이번에는 `git push`가 거부됐습니다.

이 맥에 저장된 HTTPS 자격증명과 SSH 키가 회사 계정 것이었습니다. PR을 열려는 저장소와 이 맥이 이미 갖고 있던 인증 정보가 맞지 않았습니다. gh CLI의 개인 계정을 credential helper로 붙여 해결했습니다(키가 있다는 것과 올바른 계정으로 push할 수 있다는 것은 다른 문제였습니다).

여기까지 고친 뒤에는 PR 생성 쪽이 이어졌습니다. 그런데 GitHub Pages 쪽에 남은 문제가 있었습니다.

## 인증서는 기다려도 나오지 않았습니다

자동 PR이 열리고 머지가 발행으로 이어지는 구조를 만든 뒤 GitHub Pages의 커스텀 도메인 HTTPS 인증서를 기다렸는데, 15시간이 지나도 커스텀 도메인에서 HTTPS가 준비되지 않은 상태로 남았습니다.

커스텀 도메인을 뺐다가 다시 넣었습니다. 그러자 1분 만에 인증서가 발급됐습니다. 15시간 동안 기다린 뒤에 설정을 다시 넣는 쪽으로 갔고, 이 문제는 그렇게 끝났습니다.

네 개는 전부 로컬에서는 되는데 자동 실행에서는 안 되는 부류였습니다. 바탕화면의 보호 영역이 걸렸습니다. 로그인 셸과 다른 PATH도 걸렸습니다. 이 맥에 남아 있던 회사 계정 자격증명과 기다려도 발급되지 않던 커스텀 도메인 인증서도 순서대로 걸렸습니다.

이 네 개를 다 밟고 나서야 첫 자동 PR이 열렸습니다. 세 번째 블로그를 열 때는 같은 자리에서 걸리지 않아 30분 만에 끝났습니다.
